# 引擎 ↔ 应用契约

应用与原生引擎怎样交互：输入什么、输出什么，以及混合输入协调层（`core/mixed/`）怎样调用三个引擎。这是
**契约第 1 版**（`core/mixed/snapshot.h` 中的 `kContractVersion`）。输出一侧与协调层已在开发主机上运行
（技术验证 S6，见 `platform-notes.md`）；应用还没有使用这份契约：它的三个外观类（`engine/Rime.kt`、
`Mozc.kt`、`English.kt`）仍然分别直接调用三个库，设备一侧随协调层的接入一起完成。相关的决定是 ADR-008
与 ADR-009（`decisions.md`）。

## 形态

- 一个 Kotlin 外观类对应一个原生库，只在引擎线程上调用。协调层就是这个库；它通过 librime、Mozc 与英文核心
  各自导出的普通 C 函数调用它们，所以无论一次按键问了几个引擎，都只跨一次 JNI。
- 输入：一次按键事件或一条命令，带上应用自己计数的代号。输出：一份快照，编码成字节。不用 JSON，也没有
  逐候选的 JNI 调用。
- 契约中的任何调用都不学习。学习发生在提交时，由之后的调用完成，敏感输入框永不学习。

## 输入

| 调用 | 携带 | 第 1 版 |
|---|---|---|
| 转换 | 整个组合（字母，空格与撇号作为边界提示）与代号 | 已在主机实现：`Coordinator::Convert` |
| 按键 | 一个字符及其按下坐标，用于按键纠错 | 尚无：第 1 版交付整个组合 |
| 选择候选、选择片段、锁定片段、部分提交 | 某一代号的快照中候选或片段的序号 | 尚无；快照已带有这些命令所指的片段 |
| 撤销转换、恢复输入串、清空 | — | 尚无 |
| 设置模式与选项 | 模式、智能程度、每种跨语言转换各一个开关 | 主机：构造时的 `Options` |
| 上下文 | 光标前的文本；敏感输入框永不传入 | 尚无 |

引擎无法处理的调用（组合中有字母与分隔符以外的字符，或长于 256 字节）返回只有组合、没有候选的快照。

## 输出：快照

一份快照描述一次更新之后应用显示的内容：组合、光标与候选，最好的在前。每个候选覆盖整个组合，并保留它的
片段：每个片段对应组合中的哪一段、它的文字、读音、这一段是用哪种语言输入的，以及文字的来源。之后的修改
锁定或更换的就是这些片段，所以其它片段不会被重写。

整数一律小端。字符串是一个 `u16` 字节长度加 UTF-8 字节。

| 字段 | 类型 | 含义 |
|---|---|---|
| 魔数 | 2 字节 | `KS` |
| 版本 | u16 | 契约版本；解码方拒绝其它版本 |
| 代号 | u64 | 这份快照所回应的、应用对按键与命令的计数 |
| 阶段 | u8 | 同一代号的首批候选为 0，之后的阶段从 1 起 |
| 输入 | 字符串 | 输入时的组合 |
| 光标 | u16 | 光标在组合中的字节偏移 |
| 候选数 | u16 | 其后是这么多个候选 |
| 候选：文字 | 字符串 | 选中它时提交的内容 |
| 候选：目标语言 | u8 | 它用哪种语言写成：0 中文，1 日文，2 英文 |
| 候选：代价 | i32 | 引擎的代价，小的在前；只在同一份快照内可比 |
| 候选：标志 | u8 | 第 0 位跨语言，第 1 位模糊或纠错，第 2 位 Emoji，第 3 位覆盖整个组合 |
| 候选：片段数 | u16 | 其后是这么多个片段，按输入顺序 |
| 片段：起、止 | u16、u16 | 片段对应的组合字节范围 |
| 片段：文字 | 字符串 | 这个片段提交的内容 |
| 片段：读音 | 字符串 | 日文片段为平假名，其它为输入的字母 |
| 片段：输入语言 | u8 | 这一段是用哪种语言输入的（0、1、2 同上） |
| 片段：来源 | u8 | 0 librime，1 Mozc，2 英文词典，3 拼音 → 日文词库，4 英文 → 日文词库，5 协调层的规则（助词 は、を、へ） |
| 片段：固定 | u8 | 片段作为固定值进入 Mozc 时为 1 |

解码方检查一切：魔数、版本、每个长度是否超出缓冲区、语言与来源是否在取值范围内、每个片段的范围是否在组合
之内，以及没有多余的字节。任何一项不通过，整个缓冲区作废。

计划中的统一候选这样对应到快照：文字、目标语言与代价是候选的字段；原始输入范围、来源语言、读音、词库来源
与分段信息在片段里；模糊、跨语言与 Emoji 是标志。匹配置信度就是代价。

## 过期的更新

应用记着屏幕上那份快照的代号与阶段。新的快照只有在代号更大，或代号相同而阶段更大时才取代它
（`core/mixed/snapshot.h` 中的 `Replaces`）。其它情况一律不读取就丢弃：对旧按键迟来的回答永远不会覆盖对
新按键的回答，各语言一致。

## 协调层背后的引擎

协调层不链接任何引擎。它只问五个问题（`core/mixed/engines.h`）；在设备上，每个问题是某个引擎库在 JNI
入口之外导出的一个 C 函数，在主机上由 `core/mixed/host/` 回答。

| 问题 | 由谁回答 | 在主机上 |
|---|---|---|
| 这些字母的开头拼出哪些拼音音节 | 已部署方案的 librime 拼写表（prism），所以模糊音与纠错规则同中文模式一样生效 | `core/rime/jni/rime_spellings.h`，直接链接 |
| 转换这一串音节 | 一个 librime 会话，音节之间用撇号连接 | `core/rime/jni/rime_bridge.h`，直接链接 |
| 把这段罗马字映射为平假名 | Mozc 的罗马字表 | `kotomo_mozc_service`，请求 `kana` |
| 在固定这些片段的前提下转换这段读音 | Mozc 的转换器（`MozcEngine::PinnedConvert`） | `kotomo_mozc_service`，请求 `convert` |
| 这是不是一个英文词，有多常用 | 英文词典，精确查找 | LatinIME 核心，直接链接 |

任何回答都不在调用之间保留状态，也都不学习。主机上 Mozc 在自己的进程中运行，经一个行协议访问，因为 Mozc
只能在它自己的 Bazel 工作区内构建；协议写在 `core/mozc/kotomo_mozc_service.cc` 的开头，不属于本契约。

## 版本

字段、编码、标志或来源取值的任何改动，都在同一个变更中提升两侧的契约版本并更新两侧的测试。读到其它版本的
一侧丢弃快照；不跨版本猜测。
