## 首批候选延迟（Q2，2026-11-11）

S1 的真机基线是按下 → 候选绘制 p95 120–130 ms（Galaxy Z Fold，release，2026-11-04），从手指按下开始计时。
Kotomo 在手指抬起时才输入按键，所以这个数字还包含手指在键上停留的时间，任何键盘代码都无法缩短它。从
2026-11-11 起诊断页从按键生效开始计时（"按键生效到候选绘制"，用新的名称保存，新旧样本不会混在一起），并显示
第三个序列"每键的引擎耗时"，即引擎线程的那一部分。一个中文按键依次经过：

| 步骤 | 位置 | 模拟器，debug，2026-11-11（只是构成，不是真机延迟） |
|---|---|---|
| 抬起 → `onKey` | 输入分发 | 3–9 ms |
| `onKey` 与 `refresh` | 主线程 | 1.5–4 ms |
| 交给引擎线程、librime、交回 | 引擎线程；librime 本身 p50 2 ms、p95 21 ms（n = 41） | 两个主线程步骤之间 10–40 ms |
| `applyChinese`（组合文字、候选列表、Emoji 查找） | 主线程 | 1–5 ms |
| 绘制候选栏的下一帧 | 渲染线程 | 40–100 ms；模拟器渲染很慢（那里按下 → 键绘制 p50 67 ms，Fold 上 9–10 ms） |

测量方法：用 `adb shell input tap` 输入 `nihao`，临时加入只记录时长（不含文字）的日志。外壳内已改进：每个字母
调用 librime 的 JNI 从 6 次减为 5 次（只有标点在按键之前读取组合，因为它要先提交首选）；每次刷新只读取一次窗口
尺寸；键盘的属性没有变化时不再重绘；中文路径不再把上一个键的候选当作"已绘制"。记为差距：每键一次 JNI、带版本
快照的设计属于 Q4 的引擎 ↔ 应用契约；真机上的帧等待与引擎耗时要等用户运行新的 APK（G1 清单）才有数字。

## 已知限制

- 2026-11-09 逐项读代码的结论是 P1 并未完成：混合模式的输入与中文模式完全相同。全部缺口见 `PLAN.md` §8。

- P1 的手势、输入框适配、台湾与香港输出、候选详情、Direct Boot 和 API 37 组合属性只经过单元测试或主机测试。P1 检查清单（`tests/device/p1-checklist.md`）按屏幕所见判定，目前尚未逐条记录，因此 G1 仍为 NOT_RUN。首次解锁之前，键盘只用默认设置和内置数据输入：中文不学习、英文可用、没有日文（Mozc 的数据在凭据保护存储中）、没有剪贴板、AI 和最近使用的 Emoji。
- 英文模式由 S4 引擎提供纠错、补全与下一词预测，并传入每个字母在键上的按下位置，所以靠近邻键的点按也会考虑那个键；输入的原词始终排在第一位，空格提交的就是它。中文模式在两个最佳中文候选之后提供原样的字母。中文模式用构建时编译好的
  数据经 librime（S2）转换拼音；在混合协调层（S6）完成之前，混合模式也这样做。日文模式经 Mozc（S3，库由 `scripts/build-mozc.sh`
  构建）转换罗马字：组合显示假名，第一个候选是整句，其后是由读音预测的至多三个补全、首文节的备选与假名；回车保留假名。展开箭头打开片段：
  选择某段的候选会固定它并重新转换其余部分，缩短与延长移动它的结尾，此后回车按所见提交转换。没有 Mozc 数据的构建会在候选栏中说明。
- 在 P0 于真机上测量之前，不能对延迟、内存、APK 体积或设备端 AI 作出任何结论。
