## ADR-001 引擎

**决定。** 中文用 librime 1.17.0 与 `luna_pinyin` 方案（rime-luna-pinyin，LGPL-3.0）；日文用 Mozc 3.35.6354，客户端
与 C++ 胶水层由 Kotomo 自写；英文用 HeliBoard 4.2 维护的 AOSP LatinIME 原生建议核心，词表为 aosp-dictionaries 的
en_US。简繁转换用 OpenCC，与 librime 共用。

**原因。** 它们分别是各语言成熟的开源引擎，并能为 Android 构建（`upstream.md`）。Kotomo 自写的是混合输入协调层，
而不是切分、假名汉字转换或拼写纠错（`PLAN.md` §1）。

**没有比较。** 计划要求技术验证 S2 在中文语料上比较方案与词库；当时没有语料，直接选了 `luna_pinyin`。有了转换语料后
补做这项比较。

**重新讨论的条件。** 语料表明另一种方案或引擎明显更好，或某个上游停止维护。

## ADR-002 经会话接口调用 librime

**决定。** 桥接层驱动 librime 的会话：按键用 `process_key`，片段用 `set_input`，再迭代候选、`select_candidate` 与
`get_commit`。不写 librime 插件（`register_module`）。

**原因。** 技术验证 S2 在主机上测得 `set_input` 加候选迭代每个前缀约 0.2 ms，足够协调层按片段使用（`PLAN.md` §5.4）。

**代价。** 现在中文每键跨 5 次 JNI（`Rime.kt`）；引擎 ↔ 应用契约（`PLAN.md` §4.4）把它改为每键一次。

**重新讨论的条件。** 协调层需要 librime 的网格而不只是候选，或真机上每个片段的延迟过高。

## ADR-003 Mozc 的构建

**决定。** Mozc 与 Kotomo 的胶水层（`core/mozc/`）经 `scripts/build-mozc.sh` 用 Mozc 自身的 Bazel 构建，产出
`libkotomo_mozc.so` 与 `mozc.data`。胶水层复制进 Mozc 的工作副本，子模块保持不变；可见性用 `--nocheck_visibility`
放宽，而不打补丁。应用构建从 `build/mozc-prebuilt/` 打包产物。

**原因。** Mozc 只能用 Bazel 构建，而它的转换器层（固定片段转换，协调层的 ADR 随后写）只能在它的工作区内部调用。

**2026-11-10 修订。** Android 库起初由 GitHub Actions 构建并按哈希锁定，因为当时的开发主机是 Windows on ARM64，而
NDK 没有 aarch64 Linux 的主机工具。那个仓库已删除；开发主机现在是 x86_64 Linux，库在这台主机上构建。第一次本地构建
与锁定的哈希逐字节一致；胶水层每次改动，哈希都随之变化（同日加入了预测与固定边界）。

**重新讨论的条件。** Mozc 提供了嵌入转换器的正式途径，或构建成本妨碍发布。

## ADR-004 每个引擎一个库

**决定。** `libkotomo_rime.so`、`libkotomo_mozc.so` 与 `libkotomo_english.so` 是三个独立的共享库。每个只导出 JNI
入口（链接器版本脚本；Mozc 的构建在导出多于 JNI 时由 `build-mozc.sh` 判为失败），并按 16 KB 对齐；2026-11-10 的
release 构建中六个库都用 `llvm-readelf` 核对过。

**原因。** librime 带入 Boost，Mozc 带入 protobuf 与 abseil；只露出 JNI 能避免它们的符号冲突，而且 Mozc 的 Bazel
构建无法链接进 Gradle 的 CMake 构建。

**后果。** 照现在的库，C++ 协调层不能在进程内直接调用各引擎；它在设备上怎样调用尚待决定（`PLAN.md` §2.5 决定 4）。

## ADR-005 View 与 Compose

**决定。** 键盘与候选栏是在 Canvas 上绘制的自定义 View。键盘里的面板（Emoji、剪贴板、快捷设置）与设置应用用 Jetpack
Compose 与 Material 3。

**原因。** 技术验证 S1 测得自定义 View 的按键绘制 p95 为 19–21 ms，Compose Emoji 面板首帧 73 ms（Galaxy Z Fold，
Android 17，release）：面板可以接受，按键路径不行。输入法中的 Compose 需要视图树里有 `LifecycleOwner` 与
`SavedStateRegistryOwner`，由 `KotomoService` 提供。

**重新讨论的条件。** 测量表明某个面板或键盘达不到帧预算。

## ADR-006 预编译的中文数据与独立的部署进程

**决定。** APK 带着在构建主机上编译好的 librime 数据（`scripts/prebuild-rime.sh`），手机首次使用时不编译。设备上需要
改变数据时，librime 在独立进程（`:deploy`）中部署到暂存目录，键盘在此期间继续使用上一份构建的会话，完成后再换入新的
构建。

**原因。** 主机上一次全新部署需要 5–15 s，峰值约 294 MB，期间拒绝会话（`upstream.md`）；键盘必须能继续输入。

## ADR-007 ML Kit 带入的联网权限

**决定。** 应用自己的清单不声明任何权限，合并后的清单保留 ML Kit（写作助手）带入的 `INTERNET`、`ACCESS_NETWORK_STATE`
与绑定 AICore 的权限。Kotomo 自己的代码不建立任何连接；第一个由它自己联网的功能（词库下载）加入前先与用户确认，并
写入隐私政策。

**原因。** 这是 `PLAN.md` §2.5 决定 10 的默认做法，在恢复开发时记录下来。`PRIVACY_POLICY.md` 与 `ai.md` 已经说明了
这些权限。

**重新讨论的条件。** 用户要求一个不带 ML Kit 的构建（例如 F-Droid 不接受 ML Kit）：届时把写作助手放进单独的构建变体。

## ADR-008 协调层的位置

**决定。** 混合输入协调层（`core/mixed/`）用 C++ 写成，不链接任何引擎。在设备上它是第四个共享库
`libkotomo_core.so`，带有应用唯一的 JNI 外观；librime、Mozc 与英文核心各自的库各有一张静态的函数表，装着回答
协调层问题的少数几个普通 C 函数，并通过一个 JNI 取值函数返回它的地址，应用再把这些地址交给协调层的库
（`engine-contract.md`）。各库仍然只导出 JNI 入口：最初的方案是把这些 C 函数作为符号导出、由协调层的库链接，
在实现设备一侧时（2026-11-11）放弃了，因为函数表不需要跨库解析任何符号，在运行转换语料的主机 JVM 中原样可用，
而且没有 Mozc 的构建只需不给出它的表。这是 `PLAN.md` §2.5 决定 4 的方案 (b)（第四个库、每键跨一次
JNI），用户已于 2026-11-11 追认；这些 C 函数怎样交接是本记录自己的选择。

**原因。** Kotlin 协调层 (a) 每次按键要多次跨 JNI，并把网格与解码器放到托管堆上，违背"只跨一次"的契约。合并
成一个库 (c) 会破坏 ADR-004 的符号隔离，而且无法包含由 Bazel 单独构建的 Mozc（ADR-003）。采用 (b)，各引擎
仍是内部符号隐藏的独立库，一次按键只跨一次 JNI，同一份协调层代码在主机上面对同样的五个问题运行。

**代价。** 每个引擎库在 JNI 之外多带一小组 C 接口，每张表各有版本；应用必须先关闭协调层，再关闭被它持有句柄的
引擎。主机上 Mozc 无法链接进 CMake 程序，协调层自己的语料运行器因此经一个行服务访问它；这五个调用在设备上的延迟
尚未测量。

**何时重新讨论。** 设备上无法跨库调用表中的函数，或它们的每键开销超出延迟预算。

## ADR-009 快照格式

**决定。** 用户已于 2026-11-11 追认。引擎对每次调用回答一份快照，采用自定义的紧凑二进制编码：魔数、契约版本，然后是定长的小端整数与
带长度前缀的 UTF-8 字符串（`engine-contract.md`）。解码方检查每个长度与取值范围，不通过的缓冲区整个作废。
快照带有代号与阶段，只有更新时才取代屏幕上的那一份。

**原因。** 计划要求紧凑的二进制格式或 protobuf-lite，不用逐键 JSON。快照只有三种记录、没有可选字段，手写的
编解码每侧约一百行，不增加依赖；protobuf-lite 则会在 Mozc 库内部隐藏的那一份之外再带入一份运行时
（ADR-004）。

**何时重新讨论。** 快照出现可选或嵌套重复的结构，使手写编解码容易出错；届时换用 protobuf-lite，版本号的
约定不变。

## ADR-010 基础混合模式、空格键与回车

**决定。** 基础混合模式不另用 Kotlin 做词级合并：混合模式随协调层的设备接入一起交付，关卡 G1 只判定三种单语
模式（`PLAN.md` §2.5 决定 5，用户已于 2026-11-11 追认）。组合中空格键与回车做什么，是每种模式各自的设置项
（用户决定，2026-11-12，取代决定 6 的固定规则），选项是两组很短的固定集合，默认值如下：

| 模式 | 空格（`<mode>.space`） | 回车（`<mode>.enter`） |
|---|---|---|
| 中文 | `commit_first`；另有 `next` | `shown`（字母）；另有 `first` |
| 日文 | `next`，与日文输入法一致；另有 `commit_first` | `shown`（假名）；另有 `first` |
| 混合 | `separate`；另有 `commit_first`、`next` | `first`；另有 `shown`（字母） |

`separate` 在组合内标出一处边界、不提交任何内容。`commit_first` 提交首选候选。`next` 是转换：第一次按下把首选
候选显示在输入框里但不提交，之后每按一次换到下一个候选（最后一个之后回到第一个）；此时回车提交当前显示的候选
（两种回车选项都一样），退格回到输入时的组合串，输入一个字符则先提交该候选、再输入这个字符。其他情况下回车提交
输入框显示的组合串（`shown`）或首选候选（`first`）。

**原因。** 协调层把空格读作边界提示而不是字符（`chidai ni kai ni ikou` 与 `chidainikainiikou` 转换结果相同），
所以混合模式的默认值仍是 `separate`：空格若会提交，计划自己的整句示例就无法输入。日文模式遵从输入日文的人对
空格键的预期。中文模式保持发布时的行为。选项是固定的短列表，不是按键映射：每一项都是经过测试的行为。

**代价。** 组合内的边界只存在于混合模式：中文模式用撇号键标出边界，日文模式经 Mozc 的会话转换、没有边界；为
它们保存的 `separate` 读作该模式的默认值。在 `next` 下，长的混合组合稍后到达的完整列表在已选中候选期间不绘制，
因为它会移动所选的候选。

**何时重新讨论。** 用户对其中任何一项作出不同的决定，或者日文模式的转换移到协调层（那时那里也可以提供边界）。

## ADR-011 词库直接取自数据源

**决定。** Kotomo 不托管词库包。设置列出能在手机上顺利转换的已批准数据源（`dictionaries.md`）；下载时从作者
发布的地方取来源本身的文件，在设备上用主机测试运行的同一份 Kotlin 代码（`dictionary/Sources.kt`）转换为
PLAN §10.5 的词条模型与词库包文件。GitHub 发布附件按 GitHub 为它公布的 SHA-256 摘要核对；来源不提供校验值的
文件只受 HTTPS 保护，设置中如实写明。只接受 HTTPS，重定向也一样。第一次下载之前显示一次说明，写明要连接的主机，
并说明不发送任何输入内容；每个说明版本接受一次（`state.json` 的 `online_accepted`）。这取代了带自建 SHA-256
清单与签名的托管目录（`PLAN.md` §2.5 决定 2 与 9）；`build-lock.json` 中固定的哈希只用于主机构建。

**原因。** 用户决定（2026-11-11）：不需要托管，也没有要签名的发布，词库与来源保持同样新。Q6 实测，中文与英文
词表在设备上转换可行；需要重型工具或过大的来源不可行，设置中不提供。

**代价。** 只有 GitHub 发布附带公布的校验值；普通文件（THUOCL、rime-ice 的单字表）只能信任到 HTTPS 为止。
来源改变文件结构后，它的下载会失败，直到转换器跟上。转换在后台占用手机的 CPU 与内存几秒到几十秒。

**何时重新讨论。** 来源迁移或改格式；来源开始发布校验值或签名；或者某个大的来源（Mozc 用户词典能读取之后的
日文词库）终究需要预先转换。

## ADR-012 用户词库的密码保护

**决定。** 一个默认关闭的开关（用户决定，2026-11-11），用用户设置的密码派生的密钥加密用户的词库文件
（`user.kenc`、`user.prev.kenc`）与导出文件：PBKDF2-HMAC-SHA256、600,000 轮、随机盐，每个文件 AES-256-GCM，
带版本的文件头（`dictionaries.md`）。密码与密钥从不写出；忘记的密码无法找回。librime 只能读明文词表，因此：进程
启动后词库处于锁定状态（不显示、不修改），但上次解锁时写出的词表保留，键盘仍能打出这些词；"立即锁定"清空由用户的
词生成的两份词表，直到下次解锁。

**原因。** 它保护静态时最重要的东西——带来源的完整词表、上一个版本——以及由它导出或备份的每个文件，同时不必让键盘
在每次进程重启后要求输入密码（Android 经常重启输入法）。应用私有存储中的明文词表是输入法打出这些词所必需的；其中
只有词、拼音与权重，没有日文与英文条目，也没有来源。

**代价。** 键盘能使用这些词期间，能读取应用私有存储的人（root、调试构建上的调试器）可以读到这些词表。要把它们也
保护起来，就得在每次进程启动时清空词表，用户的词在设置中解锁之前都不可用。

**何时重新讨论。** 用户决定重启也要锁定键盘（每次启动清空词表）、由键盘要求输入密码，或者改用 Keystore 中的密钥
代替密码。

## ADR-013 已学习读法的可选加密

**决定。** 一个默认关闭的开关（用户决定，2026-11-12："可选加密"；2026-11-13：用 Keystore 密钥，并支持
导入导出），把混合模式学到的读法加密保存在
`learned.kenc`，取代明文的 `learned.json`（`settings-format.md`）：AES-256-GCM，密钥是 Android Keystore 中的
`kotomo_learned`，容器布局与剪贴板历史相同。开启或关闭时以另一种形式重写文件，新文件写到磁盘之后才删除旧文件。
学习的内容，以及哪些地方不学习（敏感输入框、要求不学习的输入框、无痕模式），都不变。已学习读法页把它们导出为
带版本的明文 JSON（设备上的文件已加密时也一样），并以合并的方式导入这样的文件：双方都有的读法保留较晚使用的那份。

**原因。** `PLAN.md` §14 为学习数据写明的是 Keystore 密钥，而且键盘必须能自行读取读法：Android 经常重启输入法
进程，若用密码（ADR-012 为词库采用的方案），每次重启后读法都处于锁定状态，直到用户打开设置输入密码，于是大部分
时间里学到的内容既不能使用也不能记录。Keystore 密钥保护静态时的文件（拿到应用存储的副本而没有设备的 Keystore
就读不出），并且不需要用户做任何事。

**代价。** 它挡不住能在已解锁的设备上以本应用身份运行代码的人（root、调试构建上的调试器）：Keystore 会为应用
解密。Keystore 若丢失密钥，加密的读法随之丢失（文件被移到一旁，学习从空开始）。密钥不能离开设备，所以导出的
文件不加密；页面上写明了这一点。

**何时重新讨论。** 用户希望像词库那样为已学习的读法设置密码，或者词库也改用 Keystore 密钥。
