## First-candidate latency (Q2, 2026-11-11)

S1's device baseline, press → candidates drawn p95 120–130 ms (Galaxy Z Fold, release,
2026-11-04), counted from the touch going down. Kotomo types a key when the finger lifts, so that
number also held how long the finger rested on the key, which no keyboard code can shorten. From
2026-11-11 the diagnostics page counts from the key being typed ("Key typed to candidates drawn",
stored under a new name so old and new samples never mix) and shows a third series, "Engine work
per key", the engine thread's share. One Chinese key goes:

| Step | Where | Emulator, debug, 2026-11-11 (composition only, not device latency) |
|---|---|---|
| Release → `onKey` | input dispatch | 3–9 ms |
| `onKey` and `refresh` | main thread | 1.5–4 ms |
| Hand-off to the engine thread, librime, hand-back | engine thread; librime's own work p50 2 ms, p95 21 ms (n = 41) | 10–40 ms between the two main-thread steps |
| `applyChinese` (composing text, candidate list, emoji lookup) | main thread | 1–5 ms |
| Next frame that draws the bar | render thread | 40–100 ms; the emulator renders slowly (press → key drawn p50 67 ms there, 9–10 ms on the Fold) |

Measured with temporary duration logs (no text) while tapping `nihao` with `adb shell input tap`.
Changed in the shell: librime gets 5 JNI crossings per letter instead of 6 (the composition is read
before the key only for punctuation, which commits the top candidate first); one window-metrics
read per refresh instead of two; the keyboard's setters skip a redraw when nothing changed; the
Chinese path's first candidate update no longer counts the previous key's list as "drawn". Left as
gaps: the per-key JNI design (one call per key with a versioned snapshot) is the engine ↔ app
contract of Q4; the frame wait and the engine time on a device are unmeasured until the user runs
the new APK (G1 checklist).

## Known limitations

- Mixed mode converts through the mixed-input coordinator since 2026-11-11 (host-verified only,
  see the table above): one composition may hold pinyin, romaji and English; space marks a
  boundary, Enter or a tap commits. Choosing or locking one piece, undo, learning, key and
  spelling correction, context and the two-stage update are not built yet (`PLAN.md` §9).

- English mode suggests corrections, completions and next words from the S4 engine, with each
  letter's tap position on its key, so a tap near a neighbouring key weighs that key too; the typed
  word stays first and is what space commits. Chinese mode offers the letters as typed after the
  two best Chinese candidates. Chinese mode converts pinyin through librime (S2) with data
  compiled at build time; Japanese
  mode converts romaji through Mozc (S3, libraries built with `scripts/build-mozc.sh`): the composition shows kana, the
  first candidate is the whole sentence, followed by up to three completions predicted from the
  reading, the first segment's alternatives and the kana; Enter keeps the kana. The expand arrow
  opens the segments: choosing one's candidate pins it and converts the rest again, Shorter and
  Longer move its end, and Enter then commits the conversion as shown. A build without Mozc's data
  says so in the candidate bar.
- P1's gestures, field adaptation, Taiwan and Hong Kong output, candidate details, Direct Boot and the API 37 composition attribute are unit- or host-tested only. The P1 checklist (`tests/device/p1-checklist.md`) is judged from the screen, and no line has been recorded yet, so G1 stays NOT_RUN. Before the first unlock the keyboard types with the defaults and built-in data only: Chinese with nothing learned, English, no Japanese (Mozc needs its data in credential-protected storage), no clipboard, AI or emoji recents.
- No claim about latency, memory, APK size or on-device AI can be made before P0 measures it on a
  device.
